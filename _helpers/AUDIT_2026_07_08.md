# Audit de code AIFlowBridge — 2026-07-08

> Périmètre : lecture statique de `src/aiflowbridge/` (gateway, telemetry, providers, config, token-counter, index).
> Les items sont classés par sévérité : **BUG** (comportement incorrect observable), **WARN** (dégradation silencieuse ou risque), **IMPROV** (qualité / robustesse).
> Chaque item inclut le fichier, la ligne approximative et une suggestion concrète.

---

## 1. BUGS

### BUG-A01 — `removeEntry` : désync entre `durations` et `recent` après un `restore()`

**Fichier** : `src/aiflowbridge/telemetry.ts` — `TelemetryStore.removeEntry()`

**Problème** : `restore()` pousse toutes les entrées de `state.recent` dans `this.recent` **et** `this.durations` (jusqu'à 1 000). Mais `applyEntryInMemory()` / `record()` pousse aussi dans `durations` (avec le cap de 1 000). Après une session longue (> 1 000 requêtes), `durations` commence à se décaler par rapport à `recent` (le ring-buffer tronque les anciennes positions). `removeEntry()` utilise alors `idx` comme index commun dans les deux tableaux, ce qui supprime la **mauvaise** entrée de `durations` — le p95 est faussé.

**Suggestion** : Stocker `durationMs` directement sur chaque `RequestTelemetry` (déjà le cas) et recalculer le p95 entièrement depuis `this.recent.map(e => e.durationMs)` sans le tableau `durations` séparé. Le cap à 1 000 pour le p95 peut être gardé en ne prenant que les `recent.slice(-1000)`.

---

### BUG-A02 — `forwardChatCompletion` : `durationMs` calculé avant la lecture complète du corps de streaming

**Fichier** : `src/aiflowbridge/gateway/server.ts` — `forwardChatCompletion()`

**Problème** : `startedAt = Date.now()` est positionné **avant** `readBody()`. Pour les réponses en streaming, `recordTelemetry` est appelée dès que `Readable.fromWeb(...).pipe(response)` est déclenché — soit bien avant que le dernier chunk SSE soit envoyé au client. La durée enregistrée reflète donc le temps jusqu'au **premier octet** de la réponse upstream, pas le temps total jusqu'au **dernier octet** (qui serait la latence perçue par le client). Pour les non-streaming, c'est correct (on attend `upstreamResponse.text()`).

**Suggestion** : Pour le chemin streaming, enregistrer la télémétrie dans le callback `response.on('finish', ...)` plutôt que juste après le `pipe()`. Capture le vrai temps de bout-en-bout côté client.

---

### BUG-A03 — `readBody` : le handler `'close'` rejette même sur une fin normale dans certains runtimes Node

**Fichier** : `src/aiflowbridge/gateway/server.ts` — `readBody()`

**Problème** : L'implémentation actuelle utilise un flag `settled` pour gérer la race `end`/`close`. La correction est correcte dans la majorité des cas. Cependant, sur Node.js ≥ 20 avec HTTP/1.1 keep-alive, l'événement `'close'` peut se déclencher **après** `'end'` même sur une connexion saine (le socket est partagé). Le flag `settled` protège bien dans ce cas. Mais le handler `'error'` **et** le handler `'close'` appellent tous les deux `settle(() => reject(...))` — si `'error'` se déclenche en premier et rejette, puis `'close'` se déclenche, le `settle` est no-op, c'est correct. **Mais** l'événement `'error'` n'est pas retiré après `'end'` (seul `settled` empêche un deuxième settle). Si le socket émet une erreur après la résolution (ex: connexion reset tardif), le handler `'error'` reste en vie et génère un `UnhandledPromiseRejection` dans le processus hôte VS Code.

**Suggestion** : Utiliser `request.removeAllListeners()` ou des handlers nommés à retirer dans le bloc `settle()`, ou mieux encore basculer sur `node:stream/promises.pipeline` + un `AbortController`.

---

### BUG-A04 — `isPortInUse` : pas de timeout sur l'événement `'error'` → fuite de socket potentielle

**Fichier** : `src/aiflowbridge/gateway/probe.ts` — `isPortInUse()`

**Problème** : `socket.setTimeout(500)` est correct, et le handler `'timeout'` appelle `socket.destroy()` + `resolve(false)`. Mais `socket.on('error', ...)` est enregistré sans appeler `socket.off('timeout', ...)` en sortie. Si le socket émet `'timeout'` **et** `'error'` quasi-simultanément (Windows WSAETIMEDOUT), les deux handlers s'exécutent — `destroy()` est appelé deux fois (safe car idempotent), mais la Promise est déjà résolue à `false`, donc pas de double-résolution. C'est safe. **En revanche**, `setTimeout` (`socket.setTimeout(500)`) et le handler correspondant ne sont jamais retirés si `'connect'` ou `'error'` se déclenche en premier — le timer reste actif jusqu'à ce que le socket soit GCé, ce qui peut retarder la fin du processus en test (ou ajouter du bruit dans les logs).

**Suggestion** : Appeler `socket.setTimeout(0)` dans les handlers `'connect'` et `'error'` pour annuler le timer immédiatement.

---

### BUG-A05 — `GatewayService.stop()` : les requêtes en cours ne sont pas drainées

**Fichier** : `src/aiflowbridge/gateway/server.ts` — `stop()`

**Problème** : `current.close(cb)` arrête d'accepter de nouvelles connexions mais **n'interrompt pas** les keep-alive ni les requêtes en cours sur les connexions déjà ouvertes. Le callback ne se déclenche donc jamais tant qu'un client en streaming garde la connexion ouverte (Kilo Code en mode streaming). `reloadConfiguration()` appellera alors `gateway.start()` sur le même port sans que le serveur précédent ait libéré le socket → `EADDRINUSE`.

**Suggestion** : Utiliser `server.closeAllConnections()` (Node ≥ 18.2) avant `server.close()`, ou maintenir un `Set<Socket>` et les `destroy()` manuellement sur les versions antérieures.

## 2. WARNINGS

### WARN-B01 — Mémoire non bornée : `recent` croît sans limite

**Fichier** : `src/aiflowbridge/telemetry.ts`

**Problème** : Depuis la suppression du cap (1.6.0 follow-up, cap à 100 puis supprimé entièrement), `this.recent` est un tableau non borné en mémoire. Un utilisateur intensif (scripts de test, charge CI) peut accumuler des dizaines de milliers d'entrées. Chaque `snapshot()` fait un `[...this.recent].reverse()` → allocation d'un nouveau tableau de même taille à chaque appel. Le dashboard appelle `snapshot()` à chaque `emitUpdate()`, c'est-à-dire à chaque requête. Avec 100 000 entrées, chaque requête alloue un tableau de ~100 000 objets.

**Suggestion** : Conserver `recent` non borné **sur disque** (le persister s'en charge), mais garder un plafond configurable en mémoire (ex : 10 000 entrées). `snapshot()` ne retourne que la fenêtre en mémoire ; le dashboard peut afficher "charger plus" via le persister pour les entrées plus anciennes.

---

### WARN-B02 — `forwardChatCompletion` : la clé API peut se retrouver dans les logs d'erreur

**Fichier** : `src/aiflowbridge/gateway/server.ts`

**Problème** : En cas d'erreur réseau upstream, le bloc `catch` fait :
```ts
details: error instanceof Error ? error.message : String(error),
```
Certains runtimes `fetch` (undici, node-fetch legacy) incluent l'URL complète dans le message d'erreur, et l'URL est construite depuis `provider.baseUrl`. Si un utilisateur configure une baseUrl avec un token dans le query string (`https://api.example.com/?key=sk-...`), la clé apparaîtrait dans le corps 502 renvoyé au client **et** dans les logs.

**Suggestion** : Filtrer/masquer les query params dans les messages d'erreur propagés au client. Ajouter `isValidProviderBaseUrl` pour rejeter les URLs avec credentials dans le query string.

---

### WARN-B03 — `selectProvider` : correspondance insensible à la casse uniquement sur les alias, pas sur `baseUrl`

**Fichier** : `src/aiflowbridge/providers.ts` — `selectProvider()`

**Problème** : La recherche de correspondance normalise `profile.id`, `profile.model` et `profile.label` en minuscules, mais si un client envoie `model: "DEEPSEEK-V4-FLASH"` (tout en majuscules), la comparaison `aliases.includes(candidate)` ne trouvera pas `"deepseek-v4-flash"` parce que `candidate` est déjà normalisé mais `aliases` pourraient contenir des IDs avec casse mixte (ex: modèles MiniMax `MiniMax-M3`). Vérification : `"minimax-m3"` est dans `candidates` et `aliases` contient `"MiniMax-M3".toLowerCase()` = `"minimax-m3"` → OK. Cependant si l'utilisateur configure `id: "MiniMax-M3"` dans ses providers avec un alias qui contient un caractère Unicode normalisé différemment, des faux négatifs sont possibles.

**Suggestion** : Utiliser `localeCompare` avec `{ sensitivity: 'base' }` pour la comparaison, ou documenter que les IDs sont ASCII-only.

---

### WARN-B04 — `probeServerVersion` : pas de validation de la taille du corps JSON

**Fichier** : `src/aiflowbridge/gateway/probe.ts` — `probeServerVersion()`

**Problème** : `await response.json()` n'a aucune borne sur la taille du corps. Si le port est occupé par un service hostile (ou un proxy de dev qui renvoie une grosse page HTML avec `Content-Type: application/json`), le `response.json()` peut consommer plusieurs Mo en mémoire avant d'échouer sur le parse. Le risque est faible (loopback) mais non nul (port redirigé via un tunnel).

**Suggestion** : Lire `response.text()` avec une limite de taille (ex: 4 Ko), puis `JSON.parse`. Ou vérifier `response.headers.get('content-length')` avant.

---

### WARN-B05 — `translatePayloadForUpstream` : pas de log ni de compteur quand une traduction est appliquée

**Fichier** : `src/aiflowbridge/gateway/server.ts` — `translatePayloadForUpstream()`

**Problème** : Quand `reasoning_effort` ou `reasoning` est traduit en `reasoning_split`, aucun log n'est émis. Si un utilisateur constate que son modèle MiniMax ne raisonne pas comme attendu (ex: Kilo Code envoie `reasoning_effort: "high"` mais MiniMax reçoit `reasoning_split: true` sans que l'utilisateur le sache), il n'y a aucune trace dans les logs pour diagnostiquer la traduction.

**Suggestion** : Ajouter un `logger.debug()` (niveau debug pour ne pas polluer les logs normaux) avec les champs traduits. Ou exposer les champs traduits dans la télémétrie (`RequestTelemetry.translatedFields?`).

---

### WARN-B06 — `loadConfig` : log des clés API en clair si `provider.apiKey` est dans les providers

**Fichier** : `src/aiflowbridge/config.ts` — `loadConfig()`

**Problème** : Le bloc de diagnostic (`logger.info(...)`) logue `provider.id`, `provider.model`, et `pricingStr` pour chaque provider. Il ne logue pas `apiKey`, c'est correct. Mais `normalizeProviderProfiles` conserve `apiKey: toString(candidate.apiKey)` dans le profil. Si un log plus verbeux est ajouté à l'avenir (ex: dump complet du provider pour debug), la clé serait loguée. Il n'y a pas de marqueur `@sensitive` ou de redaction sur le champ.

**Suggestion** : Soit utiliser un type `SensitiveString` opaque pour `apiKey`, soit ajouter un getter `toJSON()` sur `ProviderProfile` qui remplace `apiKey` par `"***"`.

---

### WARN-B07 — `GatewayService` : `dispose()` est `void` alors que `stop()` est `async`

**Fichier** : `src/aiflowbridge/gateway/server.ts` — `dispose()`

**Problème** : `dispose()` appelle `void this.stop()` (fire-and-forget). VS Code pousse les objets `Disposable` via `context.subscriptions.push(this.gateway)`. À la désactivation, VS Code appelle `dispose()` de manière synchrone. Puisque `stop()` est ignoré via `void`, le socket peut rester ouvert pendant quelques ms après la désactivation → les tests qui désactivent + réactivent en séquence rapide peuvent voir un `EADDRINUSE` résiduel.

**Suggestion** : Implémenter `vscode.Disposable` correctement. Soit `dispose()` appelle `stop()` sans await (acceptable si VS Code ne garantit pas l'async), soit exposer une méthode `asyncDispose(): Promise<void>` et l'appeler depuis `deactivate()` avant que VS Code appelle les disposables. `deactivate()` appelle déjà `gateway.stop()` — il suffit de retirer le `push(this.gateway)` pour éviter le double-stop, ou de rendre `stop()` idempotent (déjà le cas via la guard `if (!this.server && !this.joined)`).

## 3. AMÉLIORATIONS

### IMPROV-C01 — `percentile()` : re-tri à chaque `snapshot()` appel

**Fichier** : `src/aiflowbridge/telemetry.ts`

`percentile()` fait `[...values].sort(...)` à chaque appel. `snapshot()` est appelé dans `emitUpdate()` → à chaque requête. Avec 1 000 entrées, c'est un tri de 1 000 éléments par requête. Coût acceptable mais inutile.

**Suggestion** : Maintenir le tableau `durations` trié en permanence (insertion à la bonne position via `bisect`) ou cacher le résultat du tri tant que `durations` n'a pas changé.

---

### IMPROV-C02 — `token-counter.ts` : timeout global non annulé si `options.signal` annule avant

**Fichier** : `src/aiflowbridge/token-counter.ts` — `fetchMinimaxPromptTokens()`

Si `options.signal` est annulé avant que le timeout interne (`timeoutId`) se déclenche, `controller.abort()` est appelé (correct), mais `clearTimeout(timeoutId)` ne l'est que dans le `finally`. C'est correct dans la logique actuelle, mais si une exception synchrone se produit avant le `try` (impossible ici, mais pattern fragile), le timer fuiterait.

**Suggestion** : Déplacer le `clearTimeout(timeoutId)` dans le handler `abort` lui-même, en plus du `finally`. Pattern plus défensif.

---

### IMPROV-C03 — `buildModelCatalog` : `created` est le timestamp de l'appel, pas du modèle

**Fichier** : `src/aiflowbridge/providers.ts` — `buildModelCatalog()`

`created: Math.floor(Date.now() / 1000)` change à chaque appel à `GET /v1/models`. Les clients OpenAI-compatibles (comme Kilo Code) ne se fient pas à ce champ, mais un client qui cache le catalogue pourrait invalider son cache à chaque requête si le champ `created` diffère.

**Suggestion** : Utiliser une valeur fixe (ex: `0` ou une constante d'epoch) ou dériver le timestamp depuis le `startedAt` du `GatewayService`.

---

### IMPROV-C04 — Absence de rate limiting sur `POST /v1/chat/completions`

**Fichier** : `src/aiflowbridge/gateway/server.ts`

Le gateway est un proxy loopback, mais rien n'empêche un processus local malveillant (ou un script de test mal configuré) de saturer l'upstream en envoyant des milliers de requêtes par seconde. Il n'y a pas de concurrency limit ni de queue.

**Suggestion** : Ajouter un compteur de requêtes en vol (`inFlightRequests`) et retourner `429 Too Many Requests` si le seuil est dépassé (ex: 20 requêtes simultanées). Configurable via `aiflowbridge.gateway.maxConcurrentRequests`.

---

### IMPROV-C05 — `handleOccupiedPort` : le délai de probe (200 ms) est trop court sur les machines lentes

**Fichier** : `src/aiflowbridge/gateway/server.ts` — `handleOccupiedPort()`

`probeServerVersion(port, { timeoutMs: 200 })` peut échouer sur une machine sous charge (ex: démarrage de VS Code avec 50+ extensions). Le gateway peer répond mais plus lentement. Résultat : un `null` est retourné → le gateway tente de binder le port → `EADDRINUSE`, l'utilisateur voit un warning alors que le peer est en fait le sien.

**Suggestion** : Augmenter le timeout de probe à 500 ms (ou le rendre configurable via `aiflowbridge.gateway.probeTimeoutMs`). Ajouter une retry avec back-off exponentiel (2 tentatives, délai 100 ms entre les deux).

---

### IMPROV-C06 — `reloadConfiguration` : la gateway est stoppée même si seul un paramètre non-gateway change

**Fichier** : `src/aiflowbridge/index.ts` — `reloadConfiguration()`

`onDidChangeConfiguration` est déclenché pour **tout** changement sous `aiflowbridge.*`, y compris `aiflowbridge.telemetry.logRequests`. La gateway est alors stoppée et redémarrée inutilement, ce qui crée une brève indisponibilité pour les clients en cours (Kilo Code perd sa connexion SSE en streaming).

**Suggestion** : Vérifier si `event.affectsConfiguration('aiflowbridge.gateway')` avant de redémarrer le gateway. Pour les changements hors-gateway (telemetry, vision), appeler uniquement `updateConfig()` sans restart.

---

### IMPROV-C07 — Pas de validation que `baseUrl` dans les settings ne contient pas `/v1` en double

**Fichier** : `src/aiflowbridge/config.ts` — `loadConfig()`

`gateway.baseUrl` est lue depuis la config (`"http://127.0.0.1:8787/v1"` par défaut). `resolveUpstreamUrl(provider, "chat/completions")` ajoute le path au `provider.baseUrl`. Si un utilisateur configure `aiflowbridge.gateway.baseUrl = "http://127.0.0.1:8787/v1"` et que le même champ est utilisé comme `provider.baseUrl` (confusion courante), l'URL finale serait `http://127.0.0.1:8787/v1/chat/completions` → correct. Mais si quelqu'un configure `provider.baseUrl = "http://127.0.0.1:8787/v1"` (avec `/v1`), l'URL finale devient `http://127.0.0.1:8787/v1/chat/completions` (correct via `new URL(path, base)`). En réalité `new URL("chat/completions", "http://host/v1")` donne `http://host/chat/completions` (le `/v1` est écrasé car le path est relatif sans `/` initial). Cela **casse silencieusement** le routage si l'utilisateur omet le `/` final dans `baseUrl`.

**Suggestion** : `resolveUpstreamUrl` force déjà un `/` final (`baseUrl.endsWith('/') ? ... : baseUrl + '/'`). Ajouter une validation dans `normalizeProviderProfiles` qui loggue un avertissement si `baseUrl` contient déjà `/v1` à la fin (indice d'une configuration incorrecte).
